# 一発で通る成果物を出す

読者は「前のチャットを知らない人」。成果物は、その人が読み終えたときに **何かを判断できる** 状態になって初めて完成。修正依頼が返ってくるのは、内容が悪いからより、読者が解釈に必要な材料を渡されていないから。

## なぜ手戻りが起きたか(過去の指摘の分析)

実際に受けた指摘を分類すると、根本原因は6つに収束する。生の指摘は `references/feedback-log.md` にある(新しい指摘を受けたらそこへ追記する)。

| # | 根本原因 | 典型的な指摘 |
|---|---|---|
| 1 | **仕組みの説明を飛ばして結果を出した** | 「学習させたの? 点プロンプト? 何クラス? 初見の人もわかるように上部にまとめて」「その方式が何かわからないと結果の解釈ができない」「どういうデータを何に分類するかの基本説明が足りない」 |
| 2 | **数値だけで現物を見せなかった** | 「実際にした結果を見せて」「数値だけでなくどこをセグメンテーションしたか画像で」「原画も隣に置いて」「git で実物見ないと結局わからん」「テスト結果のグラフも貼って」 |
| 3 | **AIが勝手に決めた・省いたことに根拠がない** | 「方式Bを既定から外した根拠が書かれてない(勝手に外したのでは)」「一部しか検証しなかった納得できる理由がない」「このモデルはどういう設計判断?」「技術的に難しいのか、やらない理由があるのか、どっち?」 |
| 4 | **結論が埋もれる・重要度順になっていない** | 「最終結論を可読性高く」「重要な点を厚く最初の方に」「スコープ外は最下部に付録程度で」「1行に収めて、折り返すと見づらい」 |
| 5 | **凡例・用語・文書間の整合が崩れている** | 「凡例はブロックで。文に置くと見逃される」「社内用語が残っていて最終報告書と整合しない」「現行モデル評価に今回の追加学習分は入ってる?」 |
| 6 | **指標を信じて現物を見ていない・考察がない** | 「よく結果を見て。構造物の領域を丸ごと塗りつぶしてる。その正解はどこから来た?」「各画像の横に定性考察を(分量は画像ごとに違ってよい)」「ETAは正しくないのでは」 |

## 手順

### 0. 着手前に3つ決める

1. **読者を一人に決める。** 既定は「この件を初めて見る顧客側の技術責任者」。社内向けでも「別チャットの内容を知らない同僚」を想定する。
2. **形式を内容から選ぶ。** 表・図・HTMLページ・PRコメント・チャット返信のどれが読者の判断に最短かを考える。迷う場合は「〇〇なので表+画像のHTMLにします」と一言添えてから作る。既に走っている形式(前回と同じフォーマットで、と言われた等)は勝手に変えない。
3. **「通った」の定義を書く。** 読者がこの成果物を読んで **何を判断・実行できるか** を一文にする。書けないなら材料が足りていないので、先に検証・調査に戻る。
4. **前提が二択に割れるなら着手前に確認する。** 「付着物ごと検出するのか、対象物を検出してから付着物を見るのか」のように答えで成果物が丸ごと変わる前提は、作ってから聞かれるより先に聞く(`grilling` スキルが使える)。それ以外の細部は自分で決めて、決めたことを本文に書く。
5. **現物を先に作る。** 実データで回した結果・実際の出力・実際の差分がない状態でレポートを書き始めない。推測で書いた節は必ず指摘される。

### 1. 骨子は固定順(結論 → 仕組み → データ → 現物 → 限界 → 次)

```
1. 結論            1〜3文。数値付き。読者が判断できる形(採用/不採用/継続)
2. この仕組みは何か  ゼロから読む人向け。入力→処理→出力。用語。学習した/していない、
                   プロンプトの種類、クラス数と各クラスの意味、アノテーションの有無と方法
3. データと条件     件数、学習に使った/使っていない(held-out)を明記、正解の出所と品質
4. 結果            現物(画像・グラフ・実出力) + 数値 + 各現物への定性考察
5. 限界と未確認     確実 / 推定 / 未確認 を分けてラベル付け
6. 次のアクション   誰が何をすれば前に進むか
付録              スコープ外、再現手順、決定の経緯と却下した案
```

- 複数案の比較は **ハブ&スポーク**: ホームに最終結論と比較表、各案は別ページで冒頭に「この案は何をどうやるか」を必ず置く。ホーム→各案→ホームのリンクを両方向に張る。
- 対になる2つ(ch1/ch2、案A/案B、Before/After)は **2カラム** で画像も説明も分ける。
- 仕様書なら §2 を「クラス定義 + 却下したクラス設計」、§5 を「合格基準」、付録を「決定の経緯」に置き換える(`references/domain-rules.md` 参照)。

### 2. 書き方のルール

- **決めたこと・省いたことは全部、根拠つきで書く。** 「時間がかかるから既定から外す」「一部だけ検証する」のような判断はユーザーに見える形で書くか、やらない。書かずに省くのが最大の手戻り要因。「できない」と「やらない」は言葉を分ける。
- **非自明な手法選択には一段やさしい説明を添える。** 「自己相関が 1/e を最初に下回る点を窓長にする」のような選択は、なぜそれが妥当かを式なしで一段落。
- **不確実性はラベルで開示する。** 「確実(出典:ファイル/行)」「推定(状況証拠)」「未確認(確認方法)」。不正確なことは絶対に書かない。ETAは計測根拠がなければ出さない。
- **凡例は色チップ付きのブロックとして画像群の直上に固定する。** 「水色=ch1、白線=基準マスク」を本文の一文で済ませない。同じ凡例スタイルをページ内・ページ間で統一する。
- **用語は成果物群で統一する。** 顧客資料にある語は勝手に言い換えず、逆に社内ジャンル語を顧客文書に持ち込まない。既存ページに同じ数値・結論があるなら、新結果が出た時点で **そちらも更新する**(追記ではなく全面更新)。
- **表・ガントは1行1項目で折り返さない。** 文字が小さくなっても視認性を優先する。
- **長さは媒体に合わせる。** チャット/Teams の返信は画面1枚(15行程度)に収め、表は文章より短くなるときだけ使う。長い説明が必要なら要点を返信に、詳細をレポート/artifact に分けてリンクする。レポートは長くてよいが、結論だけで判断できる構造を守る。
- **重要な節を厚く、軽い節は軽く。** スコープ外や余力でやったことは最下部の付録に置き、本文と同じ重さにしない。
- **見出しはメッセージ、本文は結論から。** 文章の自然さは `natural-japanese` スキルがあれば併用する。
- **既存の成果物を汚さない。** 別チャットの artifact に追加するときは新ページ+リンクにし、既存ページの結論だけ必要箇所を更新する。

### 3. 分野別ルール(必ず該当節を読む)

詳細は `references/domain-rules.md`。要点:

- **画像認識・セグメンテーション・検知**: 画像そのものを出す。原画と重畳結果を **必ず並置**(重畳だけでは元がわからない)。評価画像は **全部** 載せる(良い例だけ抜かない)。点プロンプトや参照画像など **入力側も表示**。正解線があれば重ねる。学習に使った画像か held-out かを各画像で明記。指標は「何に対する何か」(参照マスクのコピーとの一致は安定性であって精度ではない)。各画像に定性考察。
- **時系列・異常検知・API**: 想定入出力をグラフにして貼る。寄与度など「なぜそのスコアか」の出力。どのAPIをいつ・どの順で叩くかの導線。
- **コード変更・PR**: 説明は「問題 → アクション」の順で重要なものを厚く先に。関心ごとが違えばPRを分ける。実物(ブランチ/PRリンク)を出す。生成物と手書き文書の両方を更新する。
- **顧客・上司への回答**: 相手の前提のどこが合っていてどこが違うかを明示。結論から。専門用語は「機能 → 名前」の順で説明。相手の質問の意図が不明なら確認する文を添える。
- **仕様書**: クラス定義、却下案とその理由、合格基準、スコープ外一覧、決定の経緯。
- **計画・ロードマップ**: まず全要求を満たす想定で引く。1行1フェーズ。未確定部分は粗くてよいと明記。
- **実装・バグ修正の完了報告(一般のソフトウェア開発)**: 実行したコマンドと出力、テスト結果(落ちたなら落ちたまま)、変更ファイル一覧、動作確認のスクショ/ログ。「動くはず」ではなく「こう動いた」。

### 4. 出す前のセルフレビュー(先方になった気で)

出す直前に、読者の立場で **ツッコミどころを列挙する**。以下を全部チェックし、直せるものは直してから出す。

- [ ] §2 だけ読んで、初見の人に仕組み(入力・処理・出力・学習の有無・クラス)がわかるか
- [ ] 「なぜこの手法/モデル/既定値/この範囲だけ?」の問いすべてに本文で答えているか
- [ ] すべての数値に「何に対して・何件で・学習に使ったか否か」がついているか
- [ ] 現物(画像・グラフ・実出力)が載っているか。画像は原画と並んでいるか。全件か
- [ ] 各現物に考察があるか。指標と見た目が食い違う箇所を指摘しているか
- [ ] 凡例が色チップ付きブロックか。ページ内・ページ間で同じ書式か
- [ ] 削ったもの・やらなかったもの・省いた検証が根拠つきで明記されているか
- [ ] 確実/推定/未確認が分かれているか。根拠なしの数字(ETA含む)がないか
- [ ] 既存ページ・既存文書と用語・数値・結論が整合しているか(古い結論が残っていないか)
- [ ] 結論だけ読んで読者が判断できるか。スコープ外は付録に下がっているか
- [ ] 対になるものは2カラムか。表は折り返していないか
- [ ] 最終メッセージに成果物の URL を直貼りしているか

チェックで3つ以上落ちるなら、まだ出さない。

### 5. 納品

- 第三者が読む成果物は既定で Artifact として公開し、最終メッセージに URL を直接書く(「artifact にあります」ではなく、リンクそのもの)。
- 最終メッセージは **結論 + URL + 未確認事項** で構成する。作業ログにしない。
- 結果が更新されたら、ホームの結論・比較表・関連ページを同時に更新する。
- 新しい指摘を受けたら `references/feedback-log.md` に日付つきで追記し、根本原因6分類のどれかに紐づける。3件以上同じ分類が増えたら本ファイルのルールを見直す。

## 参照ファイル(読む順序)

SKILL.md だけで手順・ルール・チェックリストは完結する。ただし分野別の「現物とは何か」は本文に要点しか書いていないので、成果物を作る前に次の順で読む。

1. `references/domain-rules.md` の **該当する節だけ**(画像認識なら §1、PR なら §3 …)。必須。目次が冒頭にある
2. `references/report-skeleton.md` は **HTML レポートを書くときだけ**。凡例ブロックと原画+重畳の並置は、ここのスニペットをそのまま使うのが早い
3. `references/feedback-log.md` は **読まなくてよい**。ルールの根拠であり、新しい指摘を追記するときに開く

- `references/domain-rules.md` — 分野別の詳細ルール(画像認識の掲載基準、PR説明の型、顧客回答の型、仕様書の章立て、ロードマップ)
- `references/report-skeleton.md` — HTMLレポートの節構成、凡例ブロック、原画+重畳の並置、2カラム、比較表のスニペット
- `references/feedback-log.md` — 実際に受けた指摘の要約と分類(3案件・約55件、固有名詞は一般化済み)。このスキルの根拠
