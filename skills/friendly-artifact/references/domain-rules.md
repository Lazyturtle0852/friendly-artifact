# 分野別ルール

SKILL.md の骨子(結論→仕組み→データ→現物→限界→次)を前提に、分野ごとに「現物とは何か」「必ず答える問い」を定める。該当する節だけ読めばよい。

## 目次

1. 画像認識・セグメンテーション・検知
2. 時系列・異常検知・API
3. コード変更・PR
4. 顧客・上司への回答(チャット/メール)
5. 仕様書・設計メモ
6. 計画・ロードマップ・現状整理
7. 調査・技術サーベイ・案出し

---

## 1. 画像認識・セグメンテーション・検知

**現物 = 画像そのもの。** 数値表だけの画像認識レポートは、読者にとって「何もしていない」のと同じに見える。過去の指摘で最も多かった分類。

### 掲載の基準

| ルール | 理由(実際の指摘) |
|---|---|
| 原画と推論結果(重畳)を **横に並べる** | 「セグメンテーション後だとどこが対象だったかわからなくなる。隣にオリジナルを」 |
| 複数チャンネル/クラスは **1枚に合成** した重畳も出す。原画+合成の2枚構成が基本 | 「ch1とch2を合体した画像が欲しい、全てについて。原画と合体の2画像でいいかも」 |
| 評価画像は **全件** 載せる。良い例の抜粋にしない。多いなら路線/条件ごとにグリッド化 | 「全てについて」「包括的で過不足なく」 |
| **入力側も表示する**: 点プロンプト、参照画像、固定マスク、bbox | 「点でアノテーションなら、その前のアノテーション点も表示すべき」 |
| 正解(GT)があれば輪郭線で重ねる。GT の **出所と品質** を書く(人手か、自動か、何枚か) | 「IoUの定義はわかるが、その正解はどこから来た?」 |
| 各画像に **学習に使った / held-out / 別地点・別画角** のいずれかを明記 | 「学習してない画像では検証は回した? artifact にある?」 |
| **各画像の横に定性考察**。分量は画像ごとに違ってよい。指標が高いのに見た目が悪い例は必ず指摘 | 「それぞれの画像の横に定性考察を」「対象領域を丸ごと塗りつぶしてしまっている」 |
| 凡例は **色チップ付きブロック** を画像グリッドの直上に固定。全ページ同じ書式 | 「凡例は明確に。ただの文で置くと見逃される」 |
| 撮影条件別(昼/薄暮/夜、季節、画角)に分けた表と代表画像 | 頑健性の質問は必ず来る |

### 必ず答える問い(§2「この仕組みは何か」に書く)

- 学習させたのか、させていないのか(training-free / fine-tune / from scratch)
- プロンプトは何か(点 / bbox / テキスト / 参照画像 / なし)
- アノテーションはしたのか。誰が、何枚に、点か塗りか
- クラスは何個で、それぞれ何を意味するか。背景の扱い
- 指標の定義: 何と何の IoU/Dice か。「参照マスクのコピーとの一致」は安定性の代理であって精度ではない、と正直に書く
- モデル選定の理由(なぜそのモデルなのか、なぜ他ではないのか)

### 数値の出し方

- 対象が写っていない画像を含む平均のように、分布で歪む指標は単体で出さない。条件つき(対象が写っている画像のみ、など)を主にする
- 学習ログのベスト値と評価時の値を混ぜない
- 誤検出の主因(似た色の部材を対象と誤認 等)を画像つきで挙げる

## 2. 時系列・異常検知・API

**現物 = 実出力のグラフと、実際に叩けるエンドポイント。**

- API ごとに「想定入力 → 出力」をグラフ化して README/報告書に貼る。役割が一目でわかる
- 異常スコアには **寄与度**(どのセンサー/特徴が押し上げたか)を添える。スコアだけでは運用者が動けない
- 「どの API をいつ・どの順に叩くか」の導線を書く。日次再学習モデルと過去モデルを並行で投げる等の運用手順はカタログ側に書く
- 自動設定パラメータ(時間遅れ、窓長 等)は「どう決めているか」を一段やさしく説明し、それが最適性を保証するのか初期値提示なのかを明言する
- 検証は包括的に。一部の装置・一部の方式だけ検証したなら、その理由を書く。書けない理由なら全部やる
- 「追加学習」「ファインチューニング」「再学習」のように顧客と定義がずれやすい語は、文書の冒頭で定義する

## 3. コード変更・PR

**現物 = 差分とリンク。** 説明だけの報告には「git で実物見ないと結局わからん」と返る。

### PR 説明の型

```
## 結論(何が変わり、何ができるようになったか) 1〜3行
## 問題 → アクション(重要なものから、厚く)
  1. 問題: ...  / アクション: ...  / 根拠・検証: ...
  2. ...
## 検証(実行したコマンド、結果の数値・スクショ・グラフ)
## やらなかったこと・別PRに回したこと(理由つき)
## レビューしてほしい点
```

### 実装・バグ修正の完了報告(チャット/PRコメント)

- 「実装しました」ではなく、**実行したコマンド → その出力 → 何が確認できたか** の順で書く。テストが落ちていればその出力をそのまま貼る
- 変更ファイル一覧と、各ファイルで何を変えたか1行
- 動作確認は実物で: サーバなら実リクエストとレスポンス、UIならスクショ、バッチなら実行ログの抜粋
- やっていないこと(未テストの経路、後回しにした部分)を明記する。黙って省くと「方式Bを勝手に外した」と同じ指摘になる
- notebook と .py の両方に同じ処理があるリポジトリでは、どちらを正として揃えたか、差分が残るかを書く

- 関心ごとが違う変更は **PR を分ける**。ただし「同じPRのほうが良い」とユーザーが言えば従う
- 生成文書(openapi.json 等)と手書き文書(カタログ等)の両方を更新する。片方だけは未完了
- 顧客レビューコメントへの対応は、まず「先方になった気で」ツッコミどころを列挙 → 各項目のアクション案 → 実行、の順。列挙を飛ばして直し始めない
- ユーザーが書いた文章を推敲するときは **差分がわかる形** で出す(マージしてから直す、diff を添える)

## 4. 顧客・上司への回答(チャット/メール)

**現物 = 相手の前提と自分の答えの対応関係。**

- 相手の主張・仮定を引用し、**どこが合っていてどこが違うか** を明示する。部分的に正しい場合は「〜の部分はその通り、〜は異なる」
- 結論から。前置きなし
- **長さは画面1枚以内。** 定義表・対応表・案の比較表は、相手が実際に迷っている点だけに絞る。全部載せると読まれない。詳細が必要なら別文書にしてリンク
- 専門用語は「機能 → 名前」の順(「学習のたびに調整される数値パラメータ、いわゆる重み」)
- 相手の質問の意図が読めないとき(「ファインチューニングすべき」の背後が時間なのか精度なのか)は、答えたうえで意図を確認する一文を添える
- 確認していないことは「このセッションでは確認できていない。確認方法は〜」と書く。推測を断定にしない
- 社内向けの下書きと対外向けの文面は分けて出す。対外向けは相手が知らない社内略語を使わない
- 案を出すときは箇条書きで複数案 + 各案の評価(利点・欠点・前提)。条件(例: ソフトウェア完結)が追加されたら **同じフォーマットで** 絞る

## 5. 仕様書・設計メモ

**現物 = 決定と却下案の対。** 「なぜこの設計か」「なぜ他ではないか」に答えられない仕様は必ず質問が返る。

章立て:

```
1. 目的と、これまでの検証との関係(どの結果を受けてこの仕様か)
2. クラス定義 / インタフェース定義 + 却下した設計とその理由
3. データ(教師の作り方、品質管理、枚数)
4. 構成(モデル、損失、解像度、学習条件)
5. 計測の定義(出力をどう業務指標に変換するか)
6. 評価と合格基準(数値で)
7. スコープ外(別タスク一覧。やらない理由)
8. 決定の経緯(日付、誰が、何を根拠に)
```

- 「技術的にできない」と「やらない判断をした」を分けて書く
- ユーザーが会話で決めたことは §8 に残す(「どこかに設計メモしておいて」への対応)
- 仕様書の実現報告は §6 の合格基準に対して同じ数値で報告する

---

## 6. 計画・ロードマップ・現状整理

- 現状整理は「できている / できていない / 不明」の3値で、機能ジャンルごとの表。判断根拠(ファイル、コミット、実行結果)を添える
- ロードマップはまず **全要求を満たす想定** で引き、そこから削る。削る判断はユーザーがする
- ガント/表は **1行1フェーズ**、折り返さない。文字が小さくなっても視認性優先
- 未確定部分は「粗い可視化」と明記し、精度を装わない
- フェーズは複雑性を抑えるために分ける。順序の根拠(安全側から、依存関係)を一言

---

## 7. 調査・技術サーベイ・案出し

- 案は箇条書きで複数、各案に「仕組み / 利点 / 欠点 / 前提条件 / 先行事例」
- 評価軸を先に宣言してから案を並べる
- 条件が追加されたら同じフォーマットで絞り直す
- 先行事例・論文は出典リンクつき。見つからなければ「見つからなかった」と書く
- 社内向けのカジュアル報告でも、結論 → 根拠 → 未確認、の順は崩さない
